# Next16 Loading 404 Bug

> Next.js 16 loading.tsx creates an ancestor Suspense boundary that silently breaks notFound()/redirect() status codes for ALL nested dynamic routes

Chitraket reported (2026-08-10) that many pages weren't indexed in Google and that visiting a 404 page returned HTTP 200 instead of 404. Root-caused via live curl testing + reading `node_modules/next/dist/docs` (this repo runs a pre-release/custom Next.js 16.3.0 per the root `CLAUDE.md` "not the Next.js you know" banner, so training-data assumptions about `notFound()`/`redirect()` didn't hold).

**The mechanism:** a `loading.tsx` file at a route segment (e.g. `src/app/blog/loading.tsx`) wraps that segment's `page.tsx` **and every nested child route below it** in an implicit `<Suspense>` boundary (per `loading.js` file-convention docs: "will automatically wrap the `page.js` file and any children below"). Once that boundary exists, Next.js starts streaming the HTTP response (locking status at 200) before any nested page's `notFound()` or `redirect()` call can resolve. Per Next's own docs (`loading.md` "Status Codes" section): "Because the response headers have already been sent to the client, the status code of the response cannot be updated." The result: `notFound()` still injects `<meta name="robots" content="noindex">`, and `redirect()` falls back to a `<meta http-equiv="refresh">` tag instead of a real 307/308 - both invisible to non-JS crawlers, so Google sees 200 pages with no real content (a "soft 404" / soft-redirect), exactly matching "pages not indexed."

**Confirmed live:** `/thinking/[slug]` (no ancestor `loading.tsx`) correctly returned 404 for an invalid slug. `/blog/[slug]` and `/blog/category/[slug]` (both nested under `src/app/blog/loading.tsx`) returned 200 with a noindex meta tag / meta-refresh redirect instead of 404/308.

**Fix applied:** deleted `src/app/blog/loading.tsx`; moved its skeleton UI into a **local** `<Suspense>` boundary inside `src/app/blog/page.tsx` itself (wrapping only that page's own async `BlogContent` subcomponent). A `<Suspense>` created via component composition inside one route's `page.tsx` does NOT cascade to sibling route segments the way a folder-level `loading.tsx` does - so `/blog` keeps its loading skeleton, but `/blog/[slug]` and `/blog/category/[slug]` are no longer inside any ancestor Suspense boundary and their `notFound()`/`redirect()` calls now set real status codes. Verified via local build + `yarn start` + curl: invalid slug → 404, invalid category → 404, valid category → real 308 to `/blog?category=x`.

**How to apply:** before adding a `loading.tsx` anywhere in this app, check whether any dynamic `[slug]`/`[...catch-all]` route lives *underneath* that folder. If so, do NOT use the `loading.tsx` file convention there - use a component-local `<Suspense>` inside that specific page instead, so the boundary doesn't leak into sibling routes that need real notFound()/redirect() status codes. Also relevant: `notFound()`/`redirect()` must run **before** any `await` that could suspend, and before any ancestor Suspense fallback renders - see `docs/01-app/03-api-reference/03-file-conventions/loading.md`.

Also added (same session, per direct user request, not previously present anywhere in the codebase): `src/app/error.tsx` (branded 500 fallback with retry) and `src/app/global-error.tsx` (root-layout-level fallback; must hardcode colors since it renders its own document outside `globals.css`).

See project_seo_audit_2026-08 for the earlier (2026-08-04) canonical-tag/sitemap-XML SEO audit on this same site - that one covered a different set of issues (all confirmed still fine on 2026-08-10 re-check) and predates this loading.tsx finding.

**Still flagged, not yet fixed (needs Chitraket/Tony's call, not a pure bug):** `/biochain-sourcing` is a live, orphaned page (zero internal links, absent from `sitemap.ts`, not disallowed in `robots.ts`) with near-identical title/content to `/biochain` and its own self-referencing canonical - classic duplicate-content setup that likely also contributes to "pages not indexed." Whether to 301 it into `/biochain` or keep it separate (e.g. for old ad/backlink traffic) is a business decision, not something to silently change.
